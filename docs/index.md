# sgin 故事教程：张三和李四的十次 Code Review

张三入职青石科技的第一周，被分到内部平台组。这个组维护着资产、用户、公告、字典、导入、审批和权限后台。系统不面向公网流量洪峰，但每天都有运营、运维、研发、财务在用，一旦接口语义不稳定，前端和后台配置都会跟着乱。

李四是这个组里最早使用 sgin 的人。他不是那种喜欢把框架讲成信仰的人。每次张三提交代码，他都会先问三个问题：这个接口是不是资源？这个行为是不是流程？这段重复是不是框架已经替你做了？

于是有了这套教程。

它不是 API 速查表。README 已经负责说明字段、配置和能力边界。这里更像一本工作现场里的小书：张三先用刚入职时最容易想到的方式把需求做出来，李四再把他拉回到 sgin 更自然的写法。每章都是一个具体故事，一次 code review，一组工程取舍。

## 两个主角

张三刚入职，熟悉 Go 和 Gin，也能写 GORM。他的问题不是不会写代码，而是太习惯从 handler 开始解决一切。列表接口手写分页，详情接口手写查询，上传接口塞进默认创建，权限判断散落在业务函数里。每个选择单看都能跑，放到系统里就会越来越重。

李四用 sgin 做过几轮内部系统。他知道哪些能力应该交给框架，哪些能力应该留给业务。他不追求把所有事情都塞进 ViewSet，也不会为了对齐 DRF 去复制 DRF 的每个抽象。sgin 的底子仍然是 Gin，所以 Gin 擅长的 middleware、handler、service 分层，仍然应该自然保留。

## 这本小书想解决什么

很多框架文档只告诉你“有这个字段”“可以这样配置”，但真正写业务时，难点往往是判断：

- 这个接口该用 `ModelViewSet`，还是普通 Gin handler？
- 单个 URL 还想复用分页过滤时，用什么最轻？
- 资源动作应该挂在哪里，为什么需要 dispatcher？
- 上传、导入、审批这类流程为什么不该硬塞进默认 CRUD？
- 认证失败、权限失败为什么不能随便返回一个错误？
- 自定义 API Key 为什么不需要再造 AuthRegistry？

这套教程按问题展开。每章都尽量先把张三的“低效但常见”写法讲清楚，再讲 sgin 的推荐方式和边界。

## 阅读顺序

建议从第 1 章顺着读。前四章讲资源接口的基础形态：完整 CRUD、只读资源、单路由 API、资源内额外动作。中间两章讲边界：什么时候不要用 ViewSet，以及上传为什么要单独设计。后四章讲系统化能力：权限、错误语义、分页过滤和认证扩展。

| 章节 | 故事场景 | 你会学到 |
| --- | --- | --- |

| 02 | 公告接口只有读操作，张三却差点注册完整 CRUD | `ReadOnlyModelViewSet`、只读契约、后台导入与前台读取的边界 |
| 03 | 车辆列表只有一个 URL，张三仍然想从 handler 写起 | `APIView`、单路由复用默认 Repository、什么时候不用 APIView |

| 05 | 张三想把支付、审批、导入都塞进 ViewSet | ViewSet 的边界、Gin handler + service、流程型接口分层 |

## README 和故事教程的关系

README 是规格说明。你要查字段名、配置项、路由映射、错误码，读 README 更快。

故事教程是使用判断。你要决定某个业务需求该落在哪里，读这里更合适。

两者应该互相补充，而不是重复。README 保持准确和紧凑；这里把场景、犹豫、错误写法、取舍理由和落地清单讲透。

## 贯穿全书的一条线

李四反复提醒张三：sgin 不是要替代 Gin，而是把后台 API 中最重复、最容易写散的部分收拢起来。

普通资源 CRUD，就交给 `ModelViewSet`。

只读资源，就交给 `ReadOnlyModelViewSet`。

单 URL 但还想复用默认数据链路，就用 `APIView`。

资源内动作，用 `ExtraActions`。

复杂流程、上传、导入、支付、审批、webhook、跨模型编排，回到 Gin handler + service。

权限用 middleware 和权限接口组合，别散落在业务函数里。

认证扩展尊重 Gin middleware，不额外堆一套注册表。

读完整套故事，你应该能形成一个稳定直觉：什么时候依赖 sgin，什么时候只用 Gin，什么时候该把业务逻辑沉到 service，而不是让框架边界替你背锅。
