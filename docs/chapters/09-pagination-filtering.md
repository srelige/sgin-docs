# 第 9 章：分页过滤别手搓

周五下午，张三开始做资产列表。

这个列表看起来平平无奇，但前端要求不少：按状态过滤，按负责人过滤，按名称搜索，按创建时间倒序，支持分页。

张三又想写 handler。他准备手动解析 `page`、`page_size`、`search`、`ordering`，然后根据每个查询参数拼 GORM 条件。

李四看到后叹了口气：“你又在写列表接口的日常体力活。”

## 列表接口为什么最容易重复

后台系统里的列表接口特别多。

每个列表都可能需要：

- 页码
- 每页数量
- 总数
- 搜索
- 排序
- 字段等值过滤
- 大于、小于、包含、in 等操作符
- 默认排序
- 字段白名单

如果每个 handler 都手写一遍，问题会很快出现：

- 有的接口页码从 0 开始，有的从 1 开始。
- 有的接口 `page_size` 没限制。
- 有的接口排序字段没校验。
- 有的接口搜索字段直接拼 SQL 风险很高。
- 有的接口 total 统计和列表条件不一致。

这些不是业务差异，而是列表接口的通用能力。

## sgin 的分页开关

sgin 的分页由配置控制。

当 `rest.pagination=false` 时，列表默认不分页，`page` 和 `page_size` 不会改变结果结构。

当 `rest.pagination=true` 时，列表返回分页结构：

```txt
total
page
page_size
results
```

默认页码来自 `rest.default_page`，默认每页数量来自 `rest.default_page_size`。

这让项目可以按后台系统习惯统一打开或关闭分页，而不是每个 handler 自己决定。

## 为什么 page/page_size 对常规后台足够

张三问：“DRF 有 page-number、limit-offset、cursor，sgin 为什么主要保留 page/page_size？”

李四说，DRF 面向很广的 API 场景，支持多种分页有它的价值。limit-offset 对开放 API 和灵活查询常见，cursor 对大数据量、强实时滚动、避免深分页性能问题有价值。

但 sgin 当前更偏常规后台系统。后台管理页最常见的交互就是第几页、每页多少条。运营和管理人员也更理解页码。

如果未来项目真的需要 limit-offset 或 cursor，可以再评估。但不要为了“看起来更像 DRF”提前堆复杂度。

框架能力要服务真实场景。

## 搜索不是随便 like 所有字段

张三原本想让 `search` 自动对所有字符串字段做模糊匹配。

李四立刻拦住他。

搜索字段必须显式声明。原因很简单：

- 有些字段不适合搜索。
- 有些字段没有索引。
- 有些字段包含敏感信息。
- 全字段模糊搜索会拖慢数据库。
- 自动暴露字段会破坏接口边界。

所以 sgin 要通过 `SearchFields` 明确告诉 Repository：哪些字段可以参与搜索。

## 字段过滤必须白名单

字段过滤也是一样。

如果用户传什么查询参数，后端就拿去拼数据库字段，会很危险。它可能暴露内部字段，也可能让查询变慢，还可能造成不可控 SQL 条件。

sgin 要求通过 `FilterFields` 声明允许过滤的字段。

常见过滤包括：

```txt
status=active
owner_id=12
created_at__gte=2026-01-01
created_at__lt=2026-02-01
name__contains=server
status__in=active,pending
```

未声明字段或未知操作符应该被拒绝，而不是静默忽略。这样调用方能及时发现错误，后端也不会暴露意外查询能力。

## 排序也要白名单

张三觉得排序问题不大，传什么字段就 order by 什么字段。

李四说，排序同样会影响性能和安全。

排序字段应该通过 `OrderingFields` 声明。默认排序可以通过 `DefaultOrdering` 固定。

调用方可以传：

```txt
ordering=-created_at,name
```

但只有白名单内字段会被接受。这样既保留灵活性，也避免把数据库字段随便暴露给外部。

## 什么时候自定义 Repository

张三问：“如果过滤条件很复杂，默认 Repository 不够怎么办？”

李四说，那就自定义 Repository。

默认 Repository 适合常规列表：字段过滤、搜索、排序、分页。复杂查询，比如多表 join、权限数据范围、统计聚合、特殊索引策略，可以通过自定义 Repository 或 QueryPermissions 实现。

不要在普通 handler 里重新造一套分页过滤。先判断是配置没写，还是默认能力真的不够。

## QueryPermissions 和数据范围

资产列表后来需要“运维只能看自己负责机房的资产”。这不是前端传过滤条件，而是后端根据当前用户收窄数据范围。

这种场景适合 QueryPermissions。

它和字段过滤不同：

- 字段过滤来自请求参数。
- QueryPermissions 来自权限和当前用户上下文。

两者可以组合。最终列表应该既满足用户传入的合法过滤，也满足后端强制的数据范围。

## 列表接口的测试重点

李四让张三给列表接口补测试时，不只看能不能返回 200。

更重要的是：

- 未声明过滤字段是否拒绝。
- 未知操作符是否拒绝。
- 搜索字段是否按白名单生效。
- 排序字段是否按白名单生效。
- 默认排序是否生效。
- 开启分页后 total 是否是过滤后的总数。
- 关闭分页后响应结构是否符合预期。

列表接口很容易“看起来能用”，但边界不稳。测试要覆盖这些边界。

## 这一章的判断题

李四让张三写列表前先问：

1. 是否是普通资源列表？
2. 是否可以用 `ModelViewSet` 或 `APIView` 复用默认列表逻辑？
3. 需要哪些搜索字段？
4. 允许哪些过滤字段和操作符？
5. 允许哪些排序字段？
6. 是否需要后端强制数据范围？
7. 当前项目是否真的需要 cursor，而不是普通 page/page_size？

这些问题回答清楚，列表接口通常不需要手搓。

## 张三的笔记

张三写下：

后台系统常规列表优先用 `page/page_size`、搜索、排序和字段过滤。字段必须白名单。复杂查询再自定义 Repository 或 QueryPermissions。不要每个 handler 自己解析分页过滤。
