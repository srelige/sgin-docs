# 第 6 章：上传别塞进默认 CRUD

周四早上，张三接到资产附件需求。

每个资产可以上传采购合同、验收单、照片和维修记录。前端会用 multipart 表单上传文件，同时带上一些描述字段。

张三已经很熟悉 `ModelViewSet`，于是他想把上传放进资产附件模型的 `Create` 里。反正创建一条附件记录，听起来也像 CRUD。

李四看了一眼需求，马上说：“上传不是普通 JSON Create。”

## 上传为什么容易被写乱

张三的想法很常见：文件上传最终也要入库一条记录，那就走创建接口。

问题是，上传入口不仅仅是创建数据库记录。它还要处理文件流和存储位置。

一个真实上传流程通常包括：

- 读取 multipart 文件。
- 校验文件大小。
- 校验扩展名或 MIME。
- 生成安全文件名或对象 key。
- 保存到本地目录或对象存储。
- 记录原始文件名、大小、路径、hash、上传人。
- 必要时做病毒扫描、图片尺寸检查、文档解析。
- 如果入库失败，要考虑文件回滚或清理。

这些事情和默认 JSON CRUD 的流程完全不同。

如果把它硬塞进默认 `Create`，handler 会同时处理 JSON 绑定和 multipart 文件，Serializer 也会变得尴尬。以后别人看到 `POST /attachments`，也不清楚它到底是 JSON 创建，还是文件上传。

## sgin 不自动保存文件

张三问：“那 sgin 能不能自动把文件保存到 `uploads`？”

李四说：“不能，也不应该。”

sgin 的配置里有 `rest.static_dir`，它可以作为业务上传落盘目录的默认参考。但框架不会自动保存文件，也不会自动注册静态文件服务。

原因很现实：上传策略高度业务相关。

不同系统会选择不同方案：

- 本地磁盘
- 对象存储
- 内网文件服务
- CDN 回源目录
- 临时目录加异步扫描
- 数据库只存元数据
- 小文件直接入对象存储，大文件走分片

如果框架自动保存，很容易替业务做错决定。

## 上传入口应该显式设计

李四让张三先决定路径语义。

如果附件属于某个资产，可以设计成资源内动作：

```txt
POST /assets/:id/attachments
```

如果文件是独立资源，可以设计成文件集合：

```txt
POST /files
```

如果是导入任务，可以设计成流程入口：

```txt
POST /imports/books
```

路径先表达清楚，后面实现才不会混。

## ExtraActions 里的上传

资产附件明显属于某个资产。张三可以把它作为资产资源的 detail action：

```go
sgin.ExtraAction{
    Method:  "post",
    Path:    "attachments",
    Detail:  true,
    Handler: handlers.UploadAssetAttachment,
}
```

最终路径是：

```txt
POST /assets/:id/attachments
```

这样做的好处是，上传动作仍然聚合在资产资源下，可以继承资产 ViewSet 的认证和中间件，也可以追加自己的文件校验 middleware。

但 handler 内部仍然应该调用 service 完成实际上传流程，而不是在 ViewSet 配置里堆业务。

## 普通 handler 里的上传

如果上传不属于某个资源，比如系统统一文件中心，普通 Gin handler 更清楚：

```txt
POST /files
```

handler 负责读取 multipart，请求参数和当前用户，然后交给 `FileService`。service 决定保存到哪里、如何命名、如何写入数据库、失败时如何清理。

这类入口不需要默认 Repository，也不需要 JSON Serializer。用普通 handler 并不是绕开 sgin，而是在保留 Gin 最直接的能力。

## 文件元数据和业务模型要分开想

张三最初只想在附件表里存一个 `url`。李四让他把元数据列出来：

- 原始文件名
- 存储 key 或相对路径
- 文件大小
- MIME 类型
- 上传人
- 业务归属 ID
- 上传时间
- hash 或 checksum
- 状态，比如待扫描、可用、已删除

文件本身和元数据是两件事。数据库通常存元数据和访问路径，不直接存业务文件内容。

如果将来要接对象存储，只要 service 改存储实现，接口契约和元数据结构仍然可以保持稳定。

## 安全问题不能交给默认 CRUD

上传入口天然比普通 JSON 更敏感。

李四提醒张三至少考虑：

- 限制最大文件大小。
- 限制允许的类型。
- 不信任用户上传的文件名。
- 不把文件直接保存到可执行目录。
- 避免路径穿越。
- 根据业务决定是否公开访问。
- 对敏感文件做权限校验。
- 失败时清理临时文件。

这些规则不可能由默认 CRUD 自动推断。上传必须显式设计。

## 上传后是否注册静态服务

张三问：“如果保存到 `rest.static_dir`，是不是 sgin 会自动让前端访问？”

李四说不会。

是否公开文件、通过什么 URL 公开、是否需要鉴权、是否走下载接口、是否加一次性签名，这些都属于业务决策。sgin 只提供配置位置，不替你暴露文件。

内部后台常见做法是：上传保存后，下载也走受权限保护的接口，而不是直接暴露磁盘目录。

## 这一章的判断题

李四让张三看到上传需求时先问：

1. 文件属于某个资源，还是独立文件中心？
2. 入口是业务动作，还是普通 JSON 创建？
3. 文件保存在哪里？
4. 数据库需要保存哪些元数据？
5. 谁有权限上传和下载？
6. 失败时文件和数据库如何保持一致？

这些问题回答清楚后，再决定用 ExtraActions 还是普通 handler。

## 张三的笔记

张三写下：

JSON CRUD 和 multipart 上传是两类入口。上传要显式处理文件、存储、元数据、安全和权限。`rest.static_dir` 是配置参考，不是自动上传系统。
