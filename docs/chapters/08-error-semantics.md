# 第 8 章：前端为什么分不清 401 和 403

周五上午，前端同事把张三叫过去。

“这个接口失败后，我到底该跳登录页，还是提示没有权限？”

张三打开接口响应，发现问题确实存在。有的接口没登录返回 403，有的接口没权限返回 401，有的 token 过期和权限不足用同一个错误码。前端只能写一堆猜测逻辑。

李四看完说：“认证失败和权限失败混在一起，客户端就没法稳定处理。”

## HTTP status 先表达大语义

李四先给张三划了最重要的边界：

```txt
401：身份没有成立
403：身份成立，但权限不足
```

这句话看起来简单，但能解决很多混乱。

没带 token，身份没有成立，应该是 401。

Authorization 头格式不对，身份没有成立，应该是 401。

token 无效或过期，身份没有成立，应该是 401。

账号被禁用，身份不能成立，应该是 401。

用户已经登录，但不属于需要的用户组，应该是 403。

用户已经登录，但没有对应角色或权限点，应该是 403。

动态路由权限没有配置，而接口要求配置，应该是 403。

前端看到 401，可以进入重新登录或刷新 token 流程。看到 403，应该提示当前账号没有权限，而不是把用户踢回登录页。

## 稳定错误码给细分语义

HTTP status 只给粗粒度语义。客户端、日志检索和监控还需要更细的 code。

sgin 里的认证类错误使用稳定 code，例如：

```txt
authentication_required
invalid_authorization
invalid_token
token_expired
invalid_token_type
account_disabled
invalid_credentials
invalid_refresh_token
refresh_token_expired
```

权限类错误使用稳定 code，例如：

```txt
permission_denied
admin_required
group_required
role_required
route_permission_required
route_permission_not_configured
```

张三以前喜欢把错误 message 写得很随意。李四提醒他：message 可以给人看，code 是给程序和日志系统依赖的。code 一旦稳定，前端分支、告警规则、测试断言都更可靠。

## 登录失败为什么也是 401

张三问：“用户名密码错了，是不是业务错误，应该 400？”

李四说，对于登录接口来说，用户名密码无法建立身份，本质是认证失败，返回 401 更符合语义。错误 code 可以是 `invalid_credentials`。

但 message 不应该泄漏太多信息。不要告诉攻击者是用户名不存在，还是密码错误。

稳定语义和安全提示并不冲突。

## token 过期和权限不足不能混

前端最怕两类错误混在一起。

第一类是 token 过期。前端应该尝试刷新 token，刷新失败再跳登录。

第二类是权限不足。前端应该提示无权限，或者隐藏某些操作入口。

如果两者都返回同一个 status 和同一个 code，前端只能猜。猜错了就会出现奇怪体验：用户明明只是没权限，却被踢回登录页；或者 token 已经过期，前端却只弹一个“无权限”。

sgin 把这两类拆开，是为了让客户端行为稳定。

## 后端日志也依赖稳定 code

李四给张三看了一条线上日志。

如果所有认证权限错误都叫 `error`，排查时只能靠 message 模糊搜索。不同开发者写的 message 又不一致，日志聚合很痛苦。

如果 code 稳定，就可以直接统计：

- 最近是否大量 `token_expired`
- 是否有异常多的 `invalid_token`
- 某个接口是否频繁 `route_permission_required`
- 某个角色是否缺少权限导致 `role_required`

这对后台系统排查问题很有价值。

## 测试应该断言语义

张三以前写测试只看响应不是 200。李四让他至少断言：

- 没带 token 是 401。
- token 格式错误是 401。
- token 过期是 401。
- 已登录但缺少用户组是 403。
- 已登录但缺少角色是 403。
- 已登录但缺少动态路由权限是 403。
- 错误 code 是否稳定。

这样以后改认证或权限链时，不会悄悄破坏前端契约。

## 不要在业务 handler 里随手造权限错误

张三有时会在 handler 里返回一个普通错误，然后让统一错误处理转成 500 或 400。

李四说，如果这是权限问题，就应该用权限语义表达。否则客户端看到的是业务失败，而不是访问控制失败。

更好的方式是把权限判断尽量提前放到 middleware 或权限接口里。真正必须在业务里判断的对象归属，也要返回稳定的权限错误，而不是随手写一个字符串。

## 401/403 和隐藏资源

张三问：“如果用户没有权限看某个对象，是返回 403 还是 404？”

李四说，这取决于业务安全策略。有些系统为了避免泄漏资源存在性，会对无权对象返回 404。但这应该是明确设计，而不是错误语义混乱导致的偶然结果。

sgin 给出的默认边界是身份和权限语义。特殊隐藏策略可以在业务对象权限里处理，但要保持一致。

## 这一章的判断题

李四让张三遇到错误返回前先问：

1. 用户身份是否已经成立？
2. 如果没有成立，是缺 token、token 错、token 过期，还是账号禁用？
3. 如果身份成立，是缺用户组、角色，还是权限点？
4. 前端看到这个错误后应该做什么？
5. 日志系统能不能用稳定 code 检索？

这些问题回答清楚，错误语义才不会乱。

## 张三的笔记

张三写下：

401 解决“你是谁还没确认”。403 解决“我知道你是谁，但你不能做”。HTTP status 给大语义，稳定 error code 给程序分支、日志检索和测试断言。
