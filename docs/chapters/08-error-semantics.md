# 第 8 章：前端为什么分不清 401 和 403

周五上午，前端同事把张三叫过去。

“这个接口失败后，我到底该跳登录页，还是提示没有权限？”

张三打开接口响应，发现问题确实存在。有的接口没登录返回 403，有的接口没权限返回 401，有的 token 过期和权限不足看起来差不多。前端只能写一堆猜测逻辑。

李四看完说：“认证失败和权限失败不能混在一起，但也不能把服务端内部错误细节直接丢给客户端。”

## HTTP status 先表达大语义

李四先给张三划了最重要的边界：

```txt
401：身份没有成立
403：身份成立，但权限不足
```

这句话看起来简单，但能解决很多混乱。

没带 token，身份没有成立，应该是 401。

Authorization 头格式不对，身份没有成立，应该是 401。

token 无效或过期，身份没有成立，应该是 401。

账号被禁用，身份不能成立，应该是 401。

用户已经登录，但不属于需要的用户组，应该是 403。

用户已经登录，但没有对应角色或权限点，应该是 403。

动态路由权限没有配置，而接口要求配置，应该是 403。

前端看到 401，可以进入重新登录或刷新 token 流程。看到 403，应该提示当前账号没有权限，而不是把用户踢回登录页。

## 响应格式不应该长出第四个字段

张三问：“那要不要再返回一个 `error` 字段，里面写 `token_expired`、`permission_denied` 之类的细分码？”

李四摇头。

“sgin 的响应格式已经定了，就是 `code`、`message`、`data`。客户端不应该一会儿读 `code`，一会儿又读 `error`。”

框架默认错误响应保持同一种形状：

```json
{
  "code": 401,
  "message": "Unauthorized",
  "data": {}
}
```

`code` 和 HTTP status 保持一致。前端需要判断是否重新登录，就看 401。需要判断是否无权限，就看 403。错误响应的 `data` 默认是空对象。

至于更细的认证失败原因、权限拒绝原因，可以留在服务端日志和内部排查里。它们不一定适合直接暴露给客户端。

## 不把 err.Error() 返回给用户

张三以前喜欢这么做：数据库返回什么错误，就把错误字符串塞进响应里。

李四问他：“如果错误里带了数据库驱动、SQL 片段、文件路径、内部服务地址，你也要发给用户吗？”

张三沉默了。

sgin 的框架错误处理不直接返回 `err.Error()`。客户端看到的是安全的默认 message，服务端日志里才记录原始错误。

这件事不能只靠“生产环境别这么配”。因为总有人会手抖，把线上跑成开发配置。更稳的做法是：无论开发、测试还是生产，框架默认都不把内部错误详情返回给客户端。想看详情，就看日志。

## 5xx 对客户端统一说内部错误

张三又问：“那如果以后出现 502、504 呢？message 要不要告诉前端是网关错误还是超时？”

李四说：“具体原因写日志。客户端一般只需要知道这是服务端内部问题。”

所以 sgin 面向客户端的 5xx message 统一按内部错误处理。英文是 `Internal Server Error`，中文是 `服务内部错误`。至于是数据库失败、下游服务超时、网关异常，留给日志和监控系统。

这样前端不会为了每种 5xx 写一套脆弱分支，也不会拿到不该暴露的内部细节。

## 默认英文，可以切到中文

张三说：“我们的前端默认想展示中文，能不能配置？”

李四说：“可以，但默认先用英文，方便框架开箱和国际化环境。需要中文时，在启动时切换。”

```go
app := sgin.New()
app.Language("cn")
```

master 分支内置只支持 `en` 和 `cn`。

英文默认：

```json
{
  "code": 403,
  "message": "Forbidden",
  "data": {}
}
```

中文切换后：

```json
{
  "code": 403,
  "message": "无权访问",
  "data": {}
}
```

如果传了暂时不支持的语言，比如 `app.Language("jp")`，框架会回退到英文，不会因为语言码写错导致错误处理再出错。

## 留扩展口，不急着内置全世界

张三问：“那以后要日文、韩文怎么办？”

李四说：“master 先只支持英文和中文，但接口要留好。”

业务可以先注册自己的语言包，再切换语言：

```go
app.RegisterLanguage("jp", map[int]string{
  400: "bad request jp",
})
app.Language("jp")
```

这不是承诺框架已经内置所有语言，而是给后续扩展留一个稳定位置。

## 测试应该断言语义和泄露边界

张三以前写测试只看响应不是 200。李四让他至少断言：

- 没带 token 是 401。
- token 格式错误是 401。
- token 过期是 401。
- 已登录但缺少用户组是 403。
- 已登录但缺少角色是 403。
- 已登录但缺少动态路由权限是 403。
- 响应里没有 `error` 字段。
- 内部错误不会把原始错误字符串返回给客户端。
- `app.Language("cn")` 会返回中文 message。
- 未支持语言会回退英文，自定义注册后可以生效。

这样以后改认证、权限或错误处理链时，不会悄悄破坏前端契约，也不会重新把内部错误暴露出去。

## 401/403 和隐藏资源

张三问：“如果用户没有权限看某个对象，是返回 403 还是 404？”

李四说，这取决于业务安全策略。有些系统为了避免泄漏资源存在性，会对无权对象返回 404。但这应该是明确设计，而不是错误语义混乱导致的偶然结果。

sgin 给出的默认边界是身份和权限语义。特殊隐藏策略可以在业务对象权限里处理，但要保持一致。

## 这一章的判断题

李四让张三遇到错误返回前先问：

1. 用户身份是否已经成立？
2. 如果没有成立，客户端是不是应该走重新登录或刷新 token？
3. 如果身份成立但权限不足，客户端是不是应该提示无权访问？
4. 返回给用户的 message 是否安全，是否泄露了内部错误？
5. 原始错误是否已经进入服务端日志？
6. 当前语言配置下 message 是否符合预期？

这些问题回答清楚，错误语义才不会乱。

## 张三的笔记

张三写下：

401 解决“你是谁还没确认”。403 解决“我知道你是谁，但你不能做”。响应体固定是 `code/message/data`，message 给用户看，原始错误给日志看。默认英文，`app.Language("cn")` 切到中文，5xx 对用户统一说内部错误。
