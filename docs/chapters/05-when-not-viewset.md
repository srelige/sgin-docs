# 第 5 章：不是所有接口都该进 ViewSet

张三学会 ViewSet 后，进入了短暂的兴奋期。

他发现 CRUD 可以少写很多代码，只读资源有专门入口，单 URL 可以用 APIView，资源内动作还能用 ExtraActions。于是他开始把新需求都往 ViewSet 里想。

下午产品发来一个审批需求：用户提交报销单，主管审批，财务复核，最后调用外部支付系统打款，并写审计日志。

张三第一反应是：“这也是报销单资源，那我在 Reimbursement ViewSet 里加几个 action 就行了。”

李四听完，放下水杯：“你现在把 ViewSet 当业务流程容器了。”

## ViewSet 的强项和边界

ViewSet 擅长资源接口。

资源接口的特点是：

- 主体是一个模型或资源集合。
- HTTP 动作和资源操作有稳定对应关系。
- 输入输出围绕这个模型展开。
- 权限、过滤、序列化可以作为资源配置。
- 存储动作可以通过 Repository 抽象。

但审批、支付、导入、批处理不是这种形态。

它们更像业务流程：

- 一个请求可能操作多张表。
- 请求体和任意单个模型都不完全一致。
- 需要事务编排。
- 需要调用外部服务。
- 需要状态机判断。
- 需要写审计日志。
- 失败后可能需要补偿或重试。

把这些硬塞进 ViewSet，会让 ViewSet 看起来像资源接口，内部却变成流程编排器。

## 张三的低效方案

张三草稿里准备这样做：

```txt
POST /reimbursements/:id/approve
POST /reimbursements/:id/reject
POST /reimbursements/:id/pay
POST /reimbursements/import
```

这些路径看起来都能挂在报销单资源下。但问题在于，handler 里很快会堆满流程细节：

- 检查当前状态是否允许审批。
- 判断当前用户是否是主管。
- 更新报销单状态。
- 写审批记录。
- 调用财务系统。
- 调用支付系统。
- 写审计日志。
- 捕获外部接口失败。
- 控制事务边界。

如果这些逻辑直接写在 ViewSet action handler 里，ViewSet 就不再只是路由聚合点，而成了业务服务本身。

李四说：“这不是 ExtraActions 的问题，是你的业务层缺席。”

## Gin handler + service 的推荐分层

李四让张三把审批流程拆开。

普通 Gin handler 负责 HTTP 层：

- 读取 URL 参数。
- 绑定请求体。
- 获取当前用户。
- 调用 service。
- 把 service 结果转成统一响应。

service 负责业务层：

- 状态机校验。
- 权限补充判断。
- 多表事务。
- 外部系统调用。
- 审计日志。
- 错误分类。

DAO 或 Repository 负责数据访问。

这样分层后，handler 很薄，业务流程在 service 里可以被单独测试，也不会被 ViewSet 的资源语义绑住。

## 什么时候普通 handler 更自然

李四列了一张清单，贴在张三显示器旁边。

遇到这些需求，优先考虑 Gin handler + service：

- 支付、退款、结算
- 审批、流转、状态机
- 数据导入、批处理
- webhook 回调
- 定时任务触发入口
- 多模型事务
- 跨系统同步
- 长任务启动
- 报表聚合
- 权限极其特殊的操作

这些需求不是不能挂在某个资源路径下，而是不能让 ViewSet 承担流程编排。

有时路径仍然可以长得像资源动作，比如 `/reimbursements/:id/approve`。但实现上，handler 应该非常薄，真正流程放进 service。

## ExtraActions 和普通 handler 怎么选

张三问：“那 `/tickets/:id/close` 这种关闭工单，到底算 ExtraActions 还是普通 handler？”

李四说：“看复杂度和归属。”

如果关闭工单只是修改当前工单状态，校验几条简单规则，确实属于工单资源内动作，用 ExtraActions 很合适。

如果关闭工单还要生成账单、通知多个外部系统、写多张业务表、触发异步任务，那就算路径仍挂在工单下，也应该把复杂流程沉到 service。ExtraAction 可以作为路由入口，但不要把流程写在 ViewSet 里。

换句话说，ExtraActions 解决的是“动作路由放哪”，不是“复杂业务怎么分层”。

## APIView 也不是流程容器

张三又问：“那我用 APIView 做审批入口，可以吗？”

李四说，如果只是为了注册一个 URL，APIView 并不比 Gin handler 更有价值。APIView 的价值在于复用默认 Repository、Serializer、分页过滤等资源型能力。

审批入口通常不需要这些默认链路。它需要清楚的请求体、service 和事务控制。普通 Gin handler 更直接。

不要因为 APIView 看起来轻，就把所有单 URL 流程都塞进去。

## 业务 DTO 不进框架核心

审批接口的请求体和报销单模型不同。张三想：“要不要让 sgin 提供 DTO 和校验系统？”

李四说，这类 DTO 跟业务变化强相关。今天是审批意见，明天是短信验证码，后天是风控字段。框架如果强行内置 DTO 体系，很快会变成半套业务框架，还会限制使用者。

sgin 保留的是通用 API 能力：CRUD、路由、认证、权限、分页过滤、统一响应、Serializer 扩展。

李四补了一句：“Serializer 的字段白名单能解决普通模型 CRUD 的读写边界，比如哪些字段能返回、哪些字段能写入。但它不是业务 DTO 系统。审批意见、短信验证码、风控参数、状态机输入，这些仍然应该由业务 handler 和 service 明确处理。”

复杂输入绑定、业务校验和事务编排，应该留在业务层。

## 不使用 ViewSet 不是退步

张三一开始觉得，既然用了 sgin，不用 ViewSet 好像就亏了。

李四纠正他：框架能力不是越多用越好，而是用在合适的位置。

一个清晰的 Gin handler + service，比一个塞满流程逻辑的 ViewSet 更好维护。sgin 的设计目标不是让你忘掉 Gin，而是在重复资源接口上少写代码，在复杂业务上仍然保持 Gin 的直接和自由。

## 这一章的判断题

李四让张三以后遇到复杂接口先问：

1. 这个接口是否围绕单个资源的标准动作？
2. 请求体是否和模型结构接近？
3. 是否只操作一张主表？
4. 是否不需要复杂事务和外部服务？
5. 失败语义是否简单？

如果这些答案多数是否定的，不要强塞 ViewSet。

## 张三的笔记

张三写下：

ViewSet 是资源接口工具，不是业务流程容器。资源动作可以用 ExtraActions 聚合，复杂流程要沉到 service。不要为了复用框架形式，牺牲业务边界。
