# 第 2 章：张三复制只读接口

第二天，张三接到一个更简单的需求：公告中心。

公告由运营后台统一维护，业务系统这边只提供读取接口。前端需要两个入口：公告列表和公告详情。

张三有了昨天的经验，第一反应是继续用 `ModelViewSet`。他注册完 `/announcements` 后，忽然意识到问题：完整 CRUD 会天然包含创建、更新、删除。于是他准备在权限里把写操作挡掉，或者把写方法的 handler 覆盖成 405。

李四看到他的草稿，说：“你这是用完整资源假装只读。接口契约从一开始就不清楚。”

## 只读不是权限补丁

张三以为只读资源只是权限问题：不给写权限，不就没人能写了吗？

李四提醒他，权限只能说明“谁能不能做”，路由契约说明“这个资源本来支不支持做”。这两个问题不一样。

如果一个资源天然只读，却注册了完整 CRUD，再靠权限或 handler 去挡写操作，会给后续维护者制造误解：

- 前端看到路由习惯，会以为存在创建和编辑能力。
- 后端同事看到完整 ViewSet，会误以为只是暂时没有开放权限。
- 权限配置里可能出现没有业务意义的写权限点。
- 测试用例需要额外确认那些本不该存在的写入口。

只读资源应该从注册形态上就表达“只读”。

## ReadOnlyModelViewSet 的语义

sgin 提供 `ReadOnlyModelViewSet`，只注册两个入口：

```txt
GET /resources
GET /resources/:id
```

它不是 `ModelViewSet` 的残缺版，而是另一种资源契约。

这类资源在后台系统里很常见：

- 公告读取
- 字典读取
- 分类读取
- 地区编码
- 状态枚举
- 由定时任务同步的数据
- 由另一个系统写入、本系统只展示的数据

张三的公告接口就属于这一类。

## 张三的第二版

张三把完整 ViewSet 换成只读 ViewSet。

```go
app.Register(&sgin.ReadOnlyModelViewSet[Announcement, uint]{
    Path:  "/announcements",
    Model: &Announcement{},
})
```

路由一下变得干净：

```txt
GET /announcements
GET /announcements/:id
```

没有创建，没有更新，没有删除，也不需要用权限去解释为什么写操作不能用。

李四说：“这就是契约清楚。别人看路由就知道这个资源只负责读。”

## 只读资源仍然可以有过滤和分页

张三又问：“只读 ViewSet 会不会太弱？公告列表还要按状态筛选，按发布时间排序。”

李四说，只读只是限制 HTTP 动作，不代表列表能力变少。

只读资源仍然可以使用分页、搜索、排序、字段过滤、Serializer、认证和 middleware。因为这些能力属于读取链路本身。

例如公告列表可能需要：

- 按 `status` 过滤
- 按 `published_at` 排序
- 搜索标题
- 只返回已发布公告
- 对详情做对象级读取控制

这些都不要求资源必须支持写操作。

## 后台维护在哪里做

张三继续追问：“那公告总得有人创建吧？如果不是这个 ViewSet，那后台怎么维护？”

李四给了三个常见答案：

第一种，公告由另一个后台系统维护。当前服务只同步或读取，不负责写。

第二种，公告通过导入、脚本或管理端单独流程写入。写入口不必暴露成同一个业务 API 的标准 CRUD。

第三种，未来确实需要当前服务提供公告维护能力。那时再把 `ReadOnlyModelViewSet` 改成 `ModelViewSet`，并补上相应权限、Serializer 和测试。

关键是不要提前注册现在并不存在的能力。

## “以后可能会写”不是现在注册完整 CRUD 的理由

张三说：“可是产品以后可能要公告编辑。”

李四说：“以后可能，不等于现在应该把接口开放出来。”

后台系统最怕“接口看起来能用，但业务没准备好”。一个写入口一旦出现，就会牵扯权限配置、审计、字段校验、前端误用、数据修复。为了一个可能性提前注册完整 CRUD，收益很小，风险很实在。

当写能力真正出现时，再切换成完整 ViewSet。这个修改是明确的，也能配套补测试。

## 只读不是低级需求

李四还提醒张三，不要觉得只读接口简单就随便写。

只读接口经常是系统里调用最多、缓存最多、前端依赖最重的部分。它们的契约稳定性很重要。用 `ReadOnlyModelViewSet` 明确表达只读，可以让资源边界更稳。

特别是字典、枚举、分类这类数据，一旦路由里混入写入口，后面很容易出现“谁都以为别人管写逻辑”的尴尬。

## 这一章的判断题

李四让张三给每个资源贴一个标签：

- 这个资源是否由当前服务对外提供写能力？
- 写操作是不是标准 CRUD，而不是导入或审批流程？
- 前端是否真的需要创建、更新、删除？
- 权限配置里是否应该出现写权限点？

如果这些问题的答案是否定的，就不要注册完整 CRUD。

## 张三的笔记

张三在公告接口旁边写下：

只读就是一种接口契约，不是靠权限临时挡住写操作。资源天然只读时，用 `ReadOnlyModelViewSet`，让路由本身表达真实能力。
